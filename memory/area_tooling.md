# Area Memory — `.ai/` workflow tooling

## When to read

- Before trusting `repo_lookup.py` / `/repo-explore` output, or the `Stop` hook's lint gate, or editing this repo under `.ai/scripts/`.

## Stable facts

- Status: verified
- Source: `.ai/scripts/repo_lookup.py`, `.ai/hooks/on_stop.sh`
- Fact: `repo_lookup.py` excludes `interview_prep/` from both its path walk and its ripgrep/grep fallback (`IGNORE_PARTS`, `--glob`/`--exclude-dir`). That directory holds this repo's own interview-practice answer key; before the exclusion, a query built from on-topic terms could rank `interview_prep/ANSWERS.md` above real source, spoiling the self-practice exercise. Any new exclusion mechanism added to that script must carry this exclusion forward.
- Reconsider when: `interview_prep/` is renamed/removed, or a new search path (e.g. a vector index) is added that doesn't reuse `IGNORE_PARTS`.

## Skill registration (fixed a real gap, confirmed via official docs + live test)

All 7 `.ai/skills/*/SKILL.md` files are now mirrored at `.claude/skills/<name>/SKILL.md` (the official Agent Skills location, confirmed against Anthropic's docs: "a file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy`... skills add supporting files, frontmatter, and auto-loading"). Before this, only `repo-explore` was reachable at all (via the "explore" command wrapper); the other 6 had no registration whatsoever — `Skill(diff-review)` genuinely returned "Unknown skill," confirmed independently in two separate real sessions plus this one.

- `.claude/skills/<name>/SKILL.md` gives two things a thin `.claude/commands/<name>.md` wrapper can't: the skill shows up in the available-skills list with its **real** `description` (not generic wrapper text), and it becomes **auto-loadable** — Claude can self-trigger it from that description without explicit invocation. Verified live: before migrating `diff-review`, the list showed `diff-review: Use the diff-review skill: $ARGUMENTS`; after, it showed the actual trigger description from the file's own frontmatter.
- `.ai/skills/<name>/SKILL.md` stays the canonical/documentation copy (what `AGENTS.md`'s skill-trigger table references); `.claude/skills/<name>/SKILL.md` is the registered copy. Keep both in sync when either changes — same manual-sync discipline already used for `.ai/commands/`↔`.claude/commands/`.
- Newly created/moved skill files don't register instantly — confirmed empirically (one `Skill()` call failed right after creating a file, the very next tool call's system-reminder showed it as available). Don't retry-loop on "Unknown skill"; just `Read` the `.ai/skills/<name>/SKILL.md` file directly if it's not showing up yet.
- "explore" command renamed to `repo-explore` (`.ai/commands/repo-explore.md` + `.claude/commands/repo-explore.md`) and kept as a separate file from the `repo-explore` *skill* — both are kept, by explicit choice, not a dedup. Previously it just forwarded with "Use the repo-explore skill for: $ARGUMENTS"; now its content is the skill's Purpose/Procedure/Output merged directly into the command, on top of its own extra constraints (scope cap to entry point + 3 files + tests, "do not edit anything yet", link-formatting reminder) that the skill alone never carried. The skill file itself is unchanged — still the canonical/auto-loadable copy; the command is now a fully self-contained duplicate of its content rather than a redirect.

## Stack coverage

- `build_repo_map.py`/`repo_lookup.py` were written against this repo's Django/DRF+Makefile+Docker stack and silently degraded, not just emptied out, for a non-Django stack — found live via a throwaway JS/Express sandbox (`sandbox-js-project/`, same `.ai/` tooling copied in). Fixed so far: `package.json` scripts beyond `lint`/`format` (`dev`/`start`/`build`/`test`) are now surfaced as "Quick commands" like Makefile targets are; `tests()` now also matches `*.test.js`/`*.spec.ts`; a regex-based (non-parser, best-effort) JS/TS symbol extractor was added alongside the Python `ast` one — it only catches top-level `class`/`function`/arrow-const declarations, not class *methods*, so a service class's methods won't show up in the Symbols section; `repo_lookup.py`'s `verification_command()` now suggests `npm test`/`npx jest <file>` instead of always defaulting to `pytest` when no Python project markers exist.
- Still Django-specific and not generalized (by design — no cheap generic equivalent): `django_apps()` (looks for `apps.py`) and `urls()` (looks for `urls.py`) correctly report "none detected" for a non-Django repo rather than guessing, which is honest but not useful — don't expect a module/route map for a non-Django stack.
- The JS/TS symbol regex picked up vendored third-party code too (e.g. `.pi/vendor/pi-better-snippets/*.ts` showed up in this repo's own `.ai/repo-map.md` Symbols section) since `IGNORE_PARTS` has no vendor-code exclusion the way `node_modules` is excluded. Open question, not yet fixed: should `.pi`/`vendor` dirs be excluded from the symbol scan the way `node_modules` already is?

## Gotchas

- `build_repo_map.py` writes `.ai/repo-map.md`'s per-section rows (now as markdown links, `[path](path)`), and `repo_lookup.py`'s `extract_symbols_for()` parses that file back with its own regex. These two files have an implicit format contract — changing one's output format without updating the other's parser fails silently (no error, "Relevant symbols" just goes empty for every query). Covered by `TestSymbolExtractionMatchesRepoMapFormat` in `test_repo_lookup.py`; re-run that test after touching either file's row-formatting code.
- The `Stop` hook (`.ai/hooks/on_stop.sh`) lints with `venv/bin/ruff` on the **host**, not inside the `fms-django` Docker container — this project is otherwise Docker-first. It happens to match the container's `ruff` version (0.6.4 confirmed both sides) and resolve the same `pyproject.toml`, so results currently agree, but nothing pins that; if the Docker image's ruff version drifts from the host venv, the Stop hook's verdict can silently diverge from what `pre-commit`/CI actually enforce.
- `repo_lookup.py`'s ripgrep call used to cap combined output at a flat 80 lines across *all* matching files. For a broad query containing common words ("get", "service", "task"), a repo with ~1,100 total matching lines could have its one truly distinctive hit crowded out by alphabetically-earlier files before the cap was reached. Fixed by capping matches *per file* (`rg --max-count` / `grep -m`) instead of globally — verify this is still a per-file cap, not a global one, if the script is touched again.
- `repo_lookup.py`'s test-file detection used to check for the substring `"/tests/"` (needs a leading slash) and `filename.startswith("test")` only — both written for Django's nested-per-app `tests/test_*.py` convention. A root-level `tests/` directory (no leading slash in the relative path) and Jest/Mocha's `*.test.js`/`*.spec.ts` naming matched neither, so "Nearby tests" came back empty despite real test files existing. Fixed with a shared `is_test_path()` helper (checks any path *part* equals `tests`/`test`, plus a `\.(test|spec)\.\w+$` filename suffix) used by `score_path`, `suggested_tests`, and `_text_match_bonus` alike — covered by `TestIsTestPathRecognizesNonDjangoConventions` in `test_repo_lookup.py`.
- This repo lives under a live-syncing OneDrive folder. Rapid sequential `Edit` calls to the same file can race the sync client, which silently reverts the live file to an older version and spins off a `<name>-<user>-safeBackup-000N.<ext>` copy holding the newer content. Edit tool success does not guarantee the on-disk file matches what was sent — after a burst of edits to one file, re-`Read` it and check for stray `-safeBackup-` siblings before trusting it's current.

## What actually gets used, verified via cold-start subagent tests

- A bare "explore this repository" prompt (no concrete task/bug attached), given a fully wired-up repo (`CLAUDE.md` → `.ai/AGENTS.md`, `.claude/settings.json`, full `.ai/` copy), did **not** spontaneously invoke `repo_lookup.py` or re-run `build_repo_map.py` — confirmed via the agent's own verbatim tool-call log (one `ls`/`find`, 13 `Read` calls, nothing else). It read the pre-existing `.ai/repo-map.md` as a static artifact instead. This isn't necessarily a bug: `repo-explore`'s own trigger condition is "task start when the implementation location is not already obvious" — an open-ended "explore this repo" isn't that kind of task, so manual reading was a reasonable choice. But it means the tooling's actual usage is task-driven, not triggered by generic survey prompts — don't assume AGENTS.md alone makes a cold agent reach for `repo_lookup` without a concrete thing to find.
- A cold subagent, when asked to link a file from a nested sandbox directory, self-admittedly constructed a wrong, non-cwd-grounded relative path (`../sandbox-js-project/README.md` when no real cwd justified the `../`) — confirmed by directly asking it to explain its own reasoning after the fact, which it could not produce (said it was "an error on my part, not something derived from an actual shell cwd"). A separate run, same prompt shape, used absolute paths successfully. `AGENTS.md`'s Final response rule was tightened to say "relative to the stated project root... or absolute if that root is ambiguous" specifically because of this.

## Critical: hook resolution follows the orchestrator's bash cwd, not the main repo

`.claude/settings.json` registers hooks with **relative** command paths (`bash .ai/hooks/on_stop.sh`). Confirmed the hard way: when a `Bash` tool call leaves this session's cwd inside `sandbox-js-project/` (which has its own full copy of `.ai/hooks/`), every subsequent hook firing — Stop, PreToolUse, PostToolUse — silently resolves `.ai/hooks/on_stop.sh` against the **sandbox's** copy instead of the main repo's. That script's own `REPO_ROOT` computation (`SCRIPT_DIR/../..`) then correctly resolves to `sandbox-js-project` — so it isn't buggy, it's doing exactly what it's supposed to — but it means `git status`/ruff run against the *sandbox* tree while believing it's handling the main repo's changes. Manifested as every real-repo file (`config/__init__.py`, `src/accounts/.../models.py`, ...) failing ruff with `E902 No such file or directory`, because the hook's cwd (sandbox) genuinely doesn't contain those paths.

**Rule going forward: always `cd` back to the main repo root immediately after any `sandbox-js-project`-scoped Bash command** — don't leave a Bash call's cwd pointed inside the sandbox between turns. Verified the fix works: re-running `on_stop.sh` after `cd`-ing back to the main root passes cleanly with no E902s.

## Repo-init gate (added after a real, observed gap)

The exploration gate below only covers `Edit`/`Write` — it does nothing for a pure read-only "explore this repo" session, which was exactly the gap a real separate session exposed: `.ai/repo-map.md` was missing, the agent correctly *noticed* that and cited AGENTS.md step 2, then explored manually with `cat`/`find`/`Read` anyway instead of running `build_repo_map.py`, tacking on a passive "want me to run it?" at the end instead of just doing it. Noticing a gap and still not acting on it is the same failure mode as not noticing at all.

Fix: `.ai/hooks/on_file_access.sh` now also blocks **Read** (not just Edit/Write) of any non-exempt real-source file whenever `.ai/repo-map.md` is missing or lacks the `AI-REPO-MAP:TOOLING START` marker — forcing `python3 .ai/scripts/build_repo_map.py` (an unblocked `Bash` call) to run first. No session marker needed: the file's own existence is the signal, so it unblocks the instant the agent complies, mid-session. Escape hatch: if `.ai/scripts/build_repo_map.py` doesn't exist in a repo at all, never blocks.

All three branches tested directly in an isolated throwaway directory: blocked with no map, `build_repo_map.py` itself unaffected (it's Bash, not gated), passes clean immediately after the map exists with real content — plus the no-script escape hatch confirmed separately.

## Exploration gate (hard-enforced, not advisory)

Prompted by direct, documented evidence that prose-only workflow instructions get skipped in practice — both the agent's own reasonable "just read the files" behavior observed twice in this session, and a real public report of the same failure mode costing a user $500+ in wasted sessions ([claudeissues.com/issue/49192](https://claudeissues.com/issue/49192-claude-code-agents-skip-mandatory-project-instructions-claude-md-step-zero-despi)) — AGENTS.md step 3 ("explore with repo_lookup first") is now backed by a real `PreToolUse` gate, not just documentation:

- `.ai/hooks/on_file_access.sh` blocks the **first** real-source `Edit`/`Write` each session (`permissionDecision: deny`) until either: (a) `.ai/hooks/on_mark_explored.sh` (`PostToolUse` on `Bash`) has seen a command containing `repo_lookup.py` or `build_repo_map.py` and touched a session-scoped marker, or (b) at least 2 real-source files have been `Read` first (manual-fallback path, since AGENTS.md documents that fallback too). Once either condition is met, it never blocks again that session.
- Exempt paths (never gated): `.ai/*`, `.claude/*`, `/tmp/*`, anything under `*/scratchpad/*`, and an empty path. These are workflow/meta files, not "source" the gate cares about.
- Escape hatch: if `.ai/scripts/repo_lookup.py` doesn't exist in this repo at all, the gate never fires (nothing to gate against) — verified directly by running the hook against a throwaway directory with no `.ai/scripts/`.
- All four branches tested directly, not just reasoned about: blocked after 1 read, passes after 2 reads, passes immediately once the Bash-marker path fires (0 reads), and the no-script escape hatch.
- First real trigger was a false positive against my own edit to `.claude/settings.json` before `.claude/*` was added to the exemption list — caught immediately because the gate actually fired for real, which is the point.

## Stop hook: non-blocking nudges

- `.ai/hooks/on_stop.sh` now also emits a non-blocking `hookSpecificOutput.additionalContext` nudge (via `.ai/hooks/_build_stop_nudge.py`) whenever something changed this turn and lint either passed or didn't apply — never in the lint-block path, since that already forces a continuation. Covers two things: a diff-review-skill reminder, and a best-effort check (over the transcript's last assistant text) for file paths shown as plain code spans instead of `[path](path)` links, or commands not wrapped in a code span/fence.
- This is deliberately a soft nudge, not a hard gate, per explicit user choice — regex-checking free prose for "every file reference is linked" has real false-positive/negative risk, unlike ruff's unambiguous pass/fail. Don't convert it to `decision: block` without that being asked for again.
- The "changed" count it reports is **not** a per-turn delta — this repo has zero commits, so `git status --porcelain` always reports the entire uncommitted working tree. Worded as a presence check ("there are uncommitted changes"), not a claimed count — don't reintroduce a raw number into that message, it was misleading (it printed 344 once, for the whole tree's history of edits, not "this turn").
- Hooks are session-level (configured once, not per-directory), so they already apply inside `sandbox-js-project/` too without needing a copy there.
- `bare_commands()`'s command-verb check is case-sensitive on purpose (`"make"` not `"Make"`) — a sentence like "Make sure to..." doesn't match since real shell commands are conventionally lowercase. But a *lowercase* sentence opener ("make sure to review this.", "git is the version control system...") did false-positive until a line-ending-punctuation filter was added (commands don't end in `.`/`!`/`?`; prose does) — re-verify this if the heuristic is touched again: `make sure to review this before shipping.` must stay silent, `pytest -q --no-cov` must still fire.
- Read-whole-transcript cost measured directly, not assumed: 57ms against a 3.5MB real transcript. Fine as-is; don't add a tail-read optimization without evidence it's actually slow at some larger size.
